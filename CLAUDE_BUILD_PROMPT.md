# Claude Code build brief — Devoreo Digital Product File

Build a functioning, polished local web prototype for a German medical-device engineering company. Read `data/seed.json`, the two BOM CSVs and all files in `documents/` first. Use these files rather than inventing inconsistent records. This is an internal proof of concept for developers, not a production QMS or a medical-device approval system. German user interface, English code and README. Inspect existing project first; if empty use React + TypeScript + Vite, a clean component library or CSS, localStorage for demo state and JSZip plus a PDF library for the real export. Keep dependencies minimal. No API keys, paid services, external emails, or live customer integration. Run and test locally.

## Domain and story
UL-01 is a fictional examination couch. R1/A is the historical released product revision with actuator A; R2/B is the planned revision with replacement actuator B. BeispielMed is the fictional legal manufacturer; Ergo-Tec is the contract engineering/manufacturing partner in this scenario; MusterHub is the fictional supplier. PCN-01 proposes B, it does NOT install or authorize B. The old report PB-17 only covers R1/A. Requirement MDR Annex I 20.1 is linked to risk R-04 (unintended lowering), protective measure (holding under load), instruction PA-04 and report evidence. Only suitable evidence accepted by QM closes the demo evidence point, not all product risks. An accepted package is not a series release. All other mandatory items are preconfirmed for the limited synthetic case, not actual conformity. Mark this prominently.

## Interaction design
German, desktop-first enterprise UI, calm slate/teal colors, readable typography, compact navigation, no purely decorative dashboard. Always show project UL-01, revision, current demo role and next required action. Use one shared state model, not disconnected mock screens. Put source/decision side panels next to actual records. Add a reset-demo control and prominent 'Musterprojekt / simulierte Schnittstellen' label. Four role views: Einkauf/Entwicklung, QM, OEM (incl. RA), Service. Show clear reasons when a button is disabled. Simulated roles are not real access control.

1. Projektakte: R1/R2 revision selector; R1 read-only historical evidence; R2 shows R-04 missing. Click evidence gap to open matrix and PB-17 page 2.
2. Eingang & Änderung: use prepared email PCN-01 and its real local PDF attachment; show suggested mapping to BOM position 020 (MH-A to MH-B), then confirm/correct. Deduplicate by message ID. Unknown article goes to clarification, never auto-linked. Side-by-side BOM diff, changed row highlighted. Engineer confirms impact assessment. Create QM task with owner, source, reason and due date.
3. Nachweismatrix: chain requirement -> risk -> protective measure -> PA-04 -> report; show expected R2/B vs found R1/A. Display original page 2 via PDF viewer (PDF fragment #page=2 or equivalent), not a fake preview. Explain mismatch. Other demo requirements labelled preconfirmed. For prototype focus on R-04, do not simulate full MDR compliance.
4. Partner & Zertifikate: choose company, site, activity, certificate. For patient-positioning production at main site, ISO 13485 matches scope in the source; QM must confirm. ISO 9001 mechanical engineering or storage site selection for production triggers clarification. Certificate does not prove device safety or close R-04. Public certificate source in data/certificate_source.txt. Download its actual PDF into documents/Ergo-Tec_Public_Certificates.pdf if available; otherwise link original and show unavailable local file, never create fake certificate. Source pages 1 and 3.
5. Prüfauftrag & Bericht: QM creates test request PA-04; simulated lab input selects one of the actual prepared PDF files. Load its structured metadata from seed.json; label 'simulierter Import / vorbereitete Metadaten', NOT AI extraction. Show document preview and version, review required. Wrong R1/A, draft, or negative must never close R-04. Negative creates a blocking deviation; even subsequent positive report acceptance does not automatically close deviation: QM separately documents correction and effectiveness. Positive R2/B final + authorized QM + reason can close R-04. Separate report status and review; save actor/role, timestamp, version, reason.
6. Übergabe & OEM: allow working-draft export with gap list and explicit Arbeitsstand marker. Formal handover requires accepted evidence, partner confirmation, no blocking deviations and preconfirmed demo items. Create actual frozen ZIP with PDF index, approved files in agreed demo scope (BOM R2, risk extract + recorded review, PA-04, accepted PB-18 version, QMS source if available, requirement matrix, recipient-specific decision log); exclude drafts, rejected files and internal notes. If actual certificate is missing, block formal handover until added, or explicitly run a labelled source-link-only prototype mode that is not a complete dossier. Keep package IDs P-01/P-02 and immutable snapshots; same unchanged state returns same package. OEM can download, ask a question referencing document/page, or accept specific version. QM responds and generates P-02 if evidence changes; P-01 stays intact. RA sets regulatory route with documented reasons: unresolved / internal manufacturer route confirmed / external step pending / external prerequisite fulfilled. Only authorized OEM can separately release R2/B if current package accepted, all demo conditions met and no open external prerequisite. Log decision; do not claim CE or regulatory approval. Historical R1 remains unchanged.
7. Service & Verlauf: after valid release, explicitly activate a synthetic time jump with SN-DEMO-002, real accepted package ID from current run, R2/B and delivery reference. Search serial, open built state and dossier, create SV-01 RA review task; record OEM awareness time. No real patient data, automatic regulatory reporting or retrofit. Audit timeline accessible everywhere.

## Test before handover
Successful run: PCN confirm -> impact review -> test order -> suitable final report -> QM acceptance -> partner check -> handover -> OEM acceptance -> RA route confirmed -> separate OEM release -> service time jump. Negative branch: old report, draft, negative, open deviation and external pending condition each block release; positive + separate correction closure only changes relevant statuses. Wrong role cannot perform action. Duplicate PCN/exports stay deduplicated. Refresh preserves state. Reset clears only demo session. Open actual sources and real ZIP. Check missing local certificate behavior. Build and test; write concise run instructions and flag all simulated functionality. If time is limited prioritize screens 1,2,3,5,6, then partner/service. Do not claim unimplemented functionality.
